### Blocking issue found and fixed

**1. [FIXED — critical methodological gap] The original draft left the
Hausman test's RE-model covariance type unspecified.** `hausman_test`
(Plan 03-01) just consumes whatever `.params`/`.cov` it's handed — it has
no opinion on which covariance ESTIMATOR produced them. The original Task 1
behavior said only "re-fit RandomEffects separately for the Hausman
inputs," without saying what `cov_type` to use for that refit, or whether
it should match the FE side.

**Verified live during this review** (not assumed): fitting both FE and RE
with `cov_type="unadjusted"` vs. both with `cov_type="clustered"` on the
SAME synthetic panel produces genuinely different Hausman statistics
(0.69 vs. 0.06 in the test case) — confirming that leaving this
unspecified isn't a cosmetic gap. Worse, if an executor had used
DIFFERENT `cov_type`s for the FE and RE sides of the same test (e.g. FE
with the chosen Driscoll-Kraay/clustered SE, RE with default unadjusted,
simply because each was fit for a "different purpose" in the notebook),
the resulting Hausman statistic would rest on a genuinely invalid
comparison — the classical Hausman formula assumes both covariance
matrices are estimated the same way.

**Fix applied:** Task 1's behavior and acceptance criteria now explicitly
require the Hausman-test RE fit to use the IDENTICAL `cov_type`/`cov_config`
as `final_fe_results` (the same SE methodology the Pesaran test chose for
the base model) — making the whole analysis internally consistent: one SE
choice, applied uniformly to the base model, the Hausman comparison, and
(already correctly specified) the robustness check. `compare_specifications`'s
own internal RE fit (unadjusted, for the point-estimate comparison table)
remains a deliberately separate, differently-purposed fit — the plan now
makes this distinction explicit so an executor doesn't conflate the two.
